Baseline [`6ebf1f4`](https://github.com/tarix-mp4/Portfolio/commit/6ebf1f4f61940e31f0eeab18bb9b7e9f91d0a6bd), the verified V7 Final Hotfix source on GitHub. Phase 1 reads that code and adds isolated review files. It does not alter the V7 site or its Netlify deployment.

## Architecture inventory

- Buildless static HTML with inline project/photo/preview JSON. `app.js` owns navigation, filters, screening, cursor, hero and shared frame dispatch. `cinematic.js` and `v6.js` add effects and listeners, sound has its own owner, and the native player, Geralt and scrub controls are partly separated already.
- Eight CSS files total **161,155 B** (38,741 B when gzip-compressed individually); six script files total **132,554 B** (39,847 B gzip). `index.html` is **78,788 B** (17,884 B gzip). These are file sizes, not an observed production network waterfall. There are roughly 45+ static references on an initial measured viewport as resources become eligible; photos and previews are not all loaded upfront.
- The seven WebP preview sheets plus their metadata are **3.82 MB** encoded, and the gallery's 27 WebP variants are **2.58 MB**. Nine linked PNG originals add **30.80 MB** to Git but are not all initial transfers. Video originals total **297.82 MB** and must stay out of source control. All eight are H.264/AAC; widths, durations and checksums come from the V7 inventory and verified archive.
- Good foundations include one shared application frame scheduler, visibility/screening checks, DPR and pixel caps, cached section bounds, passive pointer/scroll listeners, click-to-load video, on-demand waveform-free previews, reduced motion, semantic landmarks, existing canonical URL and crawler metadata. Preserve these principles. Incremental module migration is lower risk than a big-bang rebuild.

## Desktop lag: findings and how to isolate them

| Confidence | Finding in the existing source | What to measure next |
| --- | --- | --- |
| Confirmed workload; device effect unmeasured | `app.js` requests WebGL with `powerPreference:"low-power"`. A discrete GPU on the same machine does not mean the browser selects it. The hero executes a shaded draw roughly at a 60 Hz ceiling while visible. Desktop uses 192 × 36 strips (**13,824 triangles**) vs. the limited path 128 × 24 (**6,144**). The desktop pixel cap is 2.2M; the limited cap is 1.2M. Sustained quality reduction only starts after a long run of late paints and another >50 ms interval. | On a smooth and affected PC, record Chrome/Edge version, OS, plugged/battery state, monitor refresh rate and DPR, `chrome://gpu` Graphics Feature Status and ANGLE renderer. Compare same viewport/DPR at hardware acceleration on/off and when selecting the other GPU through OS/browser graphics preferences if available. Do not turn every browser into “high performance” by default. |
| Confirmed per-frame paint opportunity | The sculpture's draw path updates three CSS light-position custom properties; these drive radial gradients. `cinematic.css` adds masks, blending and shadows. Cursor context and tilt may be active simultaneously. GPU time is not represented by the JS draw submission timer alone. | Isolate no WebGL, paused motion, cursor-free and static-light variants. Inspect Paint, Raster, Composite Layers, GPU and Main track in Chrome Performance. Compare dropped/partial frames, CPU/GPU load and layer memory. Avoid broad permanent `will-change`; promote only while necessary. |
| Confirmed pointer cost | `app.js` writes cursor transforms and runs ancestor matching plus label writes during `pointermove`; scroll can call `elementFromPoint`. It schedules smoothing until settled. Tilt/lighting modules also listen; several cache geometry then invalidate it on scroll. Touch bypasses much of this, so “smooth on phones” is plausible without a faster GPU. | Disable cursor replacement as a separate controlled variant, keep the OS cursor, and compare trusted click-to-next-paint with pointer hover on a normal and a high-polling mouse. Coalesce pointer sampling; cache geometry outside hot paths. |
| Confirmed geometry and main-thread exposure | `video-previews.js` calls `getBoundingClientRect()` on each fine-pointer move over an active card. Its animation frame writes a CSS background position, control value, label and scale. V7's scroll choreographer caches measurements, but still iterates photo/section ranges and writes title/palette styles. Filtering takes before/after rectangles. Geralt geometry reads are mostly entrance/reposition work, not a continuous tracking loop. None of these facts alone prove forced layout during an actual affected visit. | Compare cold sprite decode versus warm scrub and filtering. Inspect Long Animation Frame script attribution and `forcedStyleAndLayoutDuration`. Batch reads before writes; use a single screen for scrub or constrain the active film row. At 3840 × 2160, a decoded RGBA sheet alone can take ~31.6 MiB; compressed kilobytes are not decoded memory. |
| Plausible, not diagnosed | Driver/ANGLE backend, extensions, energy settings, hardware acceleration, mixed monitor refresh/DPR, and integrated-vs-discrete selection can alter where the same workload lands. Multiple CSS 3D rigs and shadows can become raster/compositing cost even when the app uses one scheduler. | Record side-by-side in a clean profile and the everyday profile. Compare GPU raster and scroll frame cadence across browsers, and preserve normal browser/device defaults. An animation or framework rewrite without workload reduction won't establish causality. |

## Baseline measurement protocol

Use a clean browser with quiet tabs, desktop 1280 × 820 at DPR 1 and DPR 2, plus a physical midrange phone. With three runs per case, record 5 seconds of hero idle, 5 seconds of pointer movement, one top-to-finale scroll, a cold and warm project scrub, a click to the reel and closing it. All cases should use the same files, warmed or cold cache as stated, and the same native scroll path. Capture a DevTools Performance trace and compare the default, no WebGL, no custom cursor, and reduced-motion modes one at a time. For each, retain p50/p95 frame interval, long tasks and long animation frames, JS/layout/paint/GPU breakdown where available, page bytes, and local trusted input timings. Treat a full field INP as a separate measurement; a scripted scrub is not INP. See [browser evidence](browser-evidence.md) for what Phase 1 could run.

References: [Chrome Performance tracks](https://developer.chrome.com/docs/devtools/performance/reference), [Long Animation Frames and input diagnosis](https://developer.chrome.com/docs/modern-web-guidance/guides/performance/identify-inp-causes), [WebGL performance guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).
